# RM Context — Product Audit & Implementation Assessment

Audit date: 2026-11-05 · Audited version: 0.2.0 · Auditor: Claude Code (Opus 5.5)

## 1. Existing architecture (as found)

The repository holds **20 files and no executable code**. Everything is Markdown prompts, two JSON manifests and two PNGs.

| Area | Files | Observation |
|---|---|---|
| Plugin manifest | `.claude-plugin/plugin.json` | Valid. Has no icon, homepage or keywords. |
| Marketplace | `.claude-plugin/marketplace.json`, `marketplace.json` | **Duplicated** byte-for-byte. Source points to the placeholder `YOUR_GITHUB_USERNAME/rm-context`, so installing from it fails until edited. |
| Agents | `architecture`, `coding`, `qa`, `documentation`, `quick-qa` | 4–8 line prompts. Model aliases (`opus`/`sonnet`/`haiku`) are valid. They define no output contract, no hand-off format and no collaboration. |
| Commands | `init`, `refresh`, `status`, `find`, `graph`, `viewer`, `link` | 1–3 sentence prompts. They ask the model to "generate" artifacts but give it no generator. |
| Skills | `project-analysis`, `context-retrieval` | Describe a `.rmcontext/` layout and a graph shape in prose. Nothing enforces the shape. |
| Assets | `rm-context-logo.png`, `rm-context-banner.png` | Raster only. Retro direction, which the brief rejects. |

`claude plugin validate` passes for the manifest and for each component directory. Its one warning is `ICON_MISSING`.

## 2. Existing capabilities: what works vs. what is only described

| Capability | README claims | Reality |
|---|---|---|
| Repository scan → `.rmcontext/` | Yes | **Prompt-only.** Each run makes the model invent the structure again. The output differs from run to run and between models. |
| Graph `nodes.json` / `edges.json` | Yes | **No schema, no validator, no generator.** Edge vocabulary is inconsistent (`reads`, `writes`, and `uses` vs. the brief's `reads_from`, `writes_to`). |
| Incremental refresh | Yes | Prompt says "use git diff". There is no file-state tracking. In non-git folders (like this one) refresh cannot be incremental at all. |
| HTML viewer | Yes | **Does not exist.** The LLM hand-writes a new HTML page on every `/graph` and `/viewer` call. That is slow, expensive and non-deterministic. |
| Secret exclusion | Yes | Prose rule only, with no enforcement. |
| Cross-project link | Yes | Prompt-only. Nothing implements the split between committed data and local paths. |
| Model routing | Yes | Static frontmatter aliases. No per-project configuration and no fallback. |
| Status / freshness | Yes | Prompt-only. |

**Conclusion:** the "working" features are the agent and command registrations and the model aliases. Every data-producing feature relies on the LLM following prose. Nothing gets replaced by mocks here, because there are no implementations to replace. The prompts are the parts worth keeping, and they are folded into the new agents and skills.

## 3. Missing capabilities (against the brief)

- A deterministic core: file inventory, ignore handling, stack detection, extractors, change detection.
- A graph schema covering business, system, engineering, infrastructure and PM nodes, with evidence and confidence, plus validation, upsert, query and impact analysis.
- The professional roles: BA, SA, PM, Senior Engineer and DevOps, with collaboration contracts.
- A documentation engine: templates, metadata, status lifecycle, version history, validation, exports.
- PM data: a task schema, dependency validation, critical path, Gantt rendering, and progress based on evidence.
- A real interactive viewer that works offline.
- Configurable model routing with fallback.
- Tests and validation of any kind.
- Branding as vector assets, and a PNG listing icon.

## 4. Technical debt

1. Duplicate marketplace manifests, one with a placeholder source.
2. The viewer is regenerated by the LLM, so there is no stable artifact and the token cost repeats on every call.
3. No schema means the graph cannot be trusted for impact analysis.
4. The `coding` and `architecture` agents overlap with the Senior Engineer role in the brief.
5. The README describes features as working when they are not (the viewer, incremental refresh).
6. The repository is not under git. Nothing is versioned, so deletions are irreversible. *(Recommendation: `git init` before release.)*

## 5. Proposed architecture

The guiding principle: **deterministic work goes in code, judgement goes to agents.** Agents never hand-write JSON graphs or HTML. They call one zero-dependency Node CLI (`scripts/rmc.mjs`, Node ≥ 18, stdlib only), which validates everything it writes.

```
            ┌──────────────── Claude Code session (orchestrator) ────────────────┐
 commands/  │ /rm-context:<cmd>  → resolves model routing → delegates to 1 agent │
 skills/    │ team-workflows · documentation-engine · team playbooks            │
            └───────────────┬─────────────────────────────────────┬─────────────┘
                 agents/    │ BA · SA · PM · Senior Eng · DevOps   │ QA · Docs · Quick-QA · Architecture
                            ▼                                      ▼
            ┌────────────── scripts/rmc.mjs (deterministic core) ──────────────┐
            │ scan/refresh · graph (validate, upsert, find, impact, rtm)       │
            │ doc (new, validate, revise, status, export) · pm (validate,      │
            │ progress, gantt, critical path) · viewer · routing · handoff     │
            └───────────────────────────────┬──────────────────────────────────┘
                                            ▼
                         .rmcontext/  (derived knowledge, traceable to source)
```

Layers (mapping the brief):

| Layer | Implementation |
|---|---|
| A. Core Intelligence | `scan.mjs` (inventory, ignore, secrets, extractors, stack detection, incremental hashes), `graph.mjs` |
| B. Team agents | `agents/*.md` and team skills. Shared contract in `skills/team-workflows` |
| C. Collaboration | Shared IDs in the graph (`BR-…`, `UC-…`, `T-…`), `rmc handoff` log, workflows A–D |
| D. Documentation engine | `templates/catalog.json` and `docs.mjs` |
| E. Visualization | `viewer.mjs` (single offline HTML) and `pm.mjs` (Gantt SVG/HTML) |

Key design decisions:

- **Scanner-owned vs. agent-owned graph data.** Every node and edge carries an `origin` (`scan` | `agent` | `manual`). Refresh replaces only `scan` items from changed files. When their evidence file changes, `agent`/`manual` items are flagged `stale` rather than deleted.
- **Regex extractors, not AST.** This keeps zero dependencies. A literal syntactic fact (an import or route declaration at line N) is recorded as `verified`. Name-based resolution (test → module) is recorded as `inferred`. The ceiling is documented.
- **Metadata registry.** `documents/registry.json` holds document metadata as structured JSON. Each Markdown file gets a regenerated metadata header.
- **Approval is gated.** `rmc doc status … Approved` requires `--approved-by`. Agents are instructed never to pass it without explicit user approval.

## 6. Migration strategy (0.2.0 → 0.3.0)

- The existing `.rmcontext/` layout is kept (`manifest.json`, `INDEX.md`, `context/`, `graph/nodes.json`, `graph/edges.json`, `flows/`, `references/`, `viewer/`, `state/`). New folders are added beside it.
- On first run, `rmc init` / `rmc refresh` migrates legacy graph files: missing `origin` → `manual` and missing `confidence` → `inferred`. Legacy edge types are mapped (`reads`→`reads_from`, `writes`→`writes_to`, `uses`→`depends_on`, `imports`→`depends_on`, `contains`→`belongs_to` reversed). Unknown items are kept and reported, never dropped.
- `INDEX.md` content outside the generated markers is preserved.
- Agents: `coding` merges into `senior-engineer`. `architecture` remains as the Core Intelligence analyst. `qa`, `documentation` and `quick-qa` are kept.
- Commands: all 0.2.0 commands keep their names.
